# CI/CD Setup Guide

## Overview

This project uses GitHub Actions for CI (testing) and CD (deployment). The frontend is deployed to GitHub Pages. The backend runs on Convex cloud and is deployed automatically as part of CD.

---

## Step 1: Configure the Convex Production Dashboard

All secrets that the backend needs at runtime are set **directly in the Convex dashboard** — never in GitHub or in code.

Go to: [dashboard.convex.dev](https://dashboard.convex.dev) → select your **production** deployment → **Settings → Environment Variables**

Add the following:

| Variable | Where to get it |
|----------|----------------|
| `AUTH_GOOGLE_ID` | Google Cloud Console → APIs & Services → Credentials → your OAuth Client ID |
| `AUTH_GOOGLE_SECRET` | Same OAuth client → Client Secret |
| `JWKS` | Generated by Convex Auth — run `npx @convex-dev/auth` locally and copy the output |
| `JWT_PRIVATE_KEY` | Generated by Convex Auth — same command as above |
| `GEMINI_API_KEY` | Google AI Studio → API Keys (Convex uses this for embeddings only — see `gemini-api-key-setup.md`) |
| `ANTHROPIC_API_KEY` | console.anthropic.com → API Keys (used by all AI flows that go through Mastra: chat, time estimation, syllabus & transcript parsing, schedule slot selection, academic profile) |
| `MASTRA_URL` | Public URL of the deployed Mastra server with `/mastra` path (e.g. `https://your-server.mastra.cloud/mastra`) — written automatically by the `deploy-mastra` job, so this is informational |
| `JHU_SIS_API_KEY` | JHU SIS portal (used for JHU course catalog lookup) |
| `CALENDAR_TOKEN_SECRET` | A random 32-byte hex string used to encrypt Google Calendar OAuth tokens — generate with `openssl rand -hex 32`. Must stay fixed across deploys, otherwise existing users' calendar tokens become unreadable. |
| `SITE_URL` | Public URL of the deployed frontend |

> **Mastra in production:** Unlike local dev (which uses ngrok), production runs Mastra on Mastra Cloud. The `deploy-mastra` job in `cd.yml` builds Mastra, deploys it via `npx mastra server deploy`, and writes the resulting URL into Convex `MASTRA_URL`. See [Mastra Setup](mastra-setup.md) for local dev configuration.

> These variables are only visible inside the Convex runtime. They are never exposed to the browser or to GitHub.

## Step 2: Configure GitHub Repository Secrets

These are used by GitHub Actions during the build and deployment process. They are never printed in logs or exposed in the built files.

Go to: GitHub repo → **Settings → Secrets and variables → Actions → New repository secret**

Add the following:

| Secret | Value |
|--------|-------|
| `CONVEX_DEPLOY_KEY` | Convex dashboard → your production deployment → Settings → Deploy Keys → Generate |
| `VITE_CONVEX_URL` | Production Convex URL (`*.convex.cloud`) — baked into the frontend build |
| `VITE_CONVEX_SITE_URL` | Production Convex HTTP host (`*.convex.site`) — used by the frontend to hit `/api/chat` and the Calendar OAuth route |
| `SITE_URL` | Public URL of the deployed frontend (CD writes this into Convex so OAuth redirects land in the right place) |
| `CALENDAR_TOKEN_SECRET` | Same value you set in Convex (Step 1) — CD re-applies it on every deploy so the secret stays stable |
| `JHU_SIS_API_KEY` | Same value you set in Convex (Step 1) — CD re-applies it on every deploy |
| `MASTRA_URL` | URL of the deployed Mastra server (`https://<deployment>.mastra.cloud/mastra`) — CD writes this into Convex after deploying Mastra |
| `MASTRA_API_TOKEN`, `MASTRA_ORG_ID`, `MASTRA_PROJECT_ID` | Mastra Cloud credentials used by the `deploy-mastra` job (`npx mastra server deploy`) |

> `VITE_CONVEX_URL` and `VITE_CONVEX_SITE_URL` are the only values baked into the frontend build. They are public Convex endpoints — not secrets per se, but kept here to avoid hardcoding environment-specific values in the repo.

> The CD workflow does **not** read Google OAuth credentials from GitHub secrets. They live in the Convex dashboard (Step 1) and are picked up by the deployed backend at runtime.

## Step 3: Configure Google Cloud Console

Go to: [console.cloud.google.com](https://console.cloud.google.com) → APIs & Services → Credentials → your OAuth 2.0 Client ID

Add these under **Authorized JavaScript origins**:
```
https://<your-org>.github.io
```

Add these under **Authorized redirect URIs** (replace `<prod-deployment>` with the prod Convex deployment subdomain — currently `dutiful-dinosaur-826`):
```
https://<prod-deployment>.convex.site/api/auth/callback/google
https://<prod-deployment>.convex.site/api/calendar/callback
```

> The redirect URIs point to Convex, not GitHub Pages. Google sends the auth code to Convex, which then redirects the user back to `SITE_URL` (your frontend). Each developer's personal Convex deployment needs its own pair of redirect URIs added too — see [`google-auth-setup.md`](google-auth-setup.md) and [`google-calendar-connection-setup.md`](google-calendar-connection-setup.md).

## How CI Works

**File:** `.github/workflows/ci.yml`

Triggers on: pull requests to `master`, `dev`, or `cicd`; and pushes to `master` or `cicd`.

Jobs:
1. **`build-and-test`** — `npm ci`, `npm run build` (catches TypeScript and build errors), `npm test` (Vitest backend + frontend).
2. **`e2e`** — runs after `build-and-test`. Installs Chromium, runs `npm run test:e2e` (Playwright against `vite preview`), uploads the `playwright-report/` artifact on failure.
3. **`deploy`** — runs after `build-and-test` only on push events. Deploys the Convex backend (`npx convex deploy`).

> The only deployment CI does is the Convex backend on push to `master`/`cicd`. Frontend and Mastra deploys live in `cd.yml`.

---

## How CD Works

**File:** `.github/workflows/cd.yml`

Triggers on: pushes to `master` or `cicd`.

Three jobs run in parallel where possible:

**`build` (frontend + Convex env)**
1. `npm ci`, install Convex CLI globally
2. `npx convex deploy` using `CONVEX_DEPLOY_KEY`
3. Re-applies `SITE_URL`, `CALENDAR_TOKEN_SECRET`, and `JHU_SIS_API_KEY` on the Convex deployment (idempotent, keeps these in sync with GitHub Secrets)
4. `npm run build` with `VITE_CONVEX_URL` and `VITE_CONVEX_SITE_URL` injected
5. Copies `frontend/dist/index.html` → `frontend/dist/404.html` so GitHub Pages serves the SPA for unknown routes
6. Uploads `frontend/dist` as a GitHub Pages artifact

**`deploy-mastra`**
1. `npm ci` in `mastra/`
2. `npx mastra build --dir src/mastra`
3. `npx mastra server deploy -y` to Mastra Cloud (uses `MASTRA_API_TOKEN`, `MASTRA_ORG_ID`, `MASTRA_PROJECT_ID`)
4. Writes the resulting URL into Convex `MASTRA_URL`

**`deploy`** — depends on `build`. Publishes the GitHub Pages artifact via `actions/deploy-pages@v4`.

> The only values baked into the frontend bundle are `VITE_CONVEX_URL` and `VITE_CONVEX_SITE_URL`. Everything else (Google keys, Gemini key, Anthropic key, JWT keys, calendar encryption secret) stays on the Convex / Mastra server and is never included in the build.

## Secret Exposure Rules

- **Never** put `AUTH_GOOGLE_SECRET`, `GEMINI_API_KEY`, `ANTHROPIC_API_KEY`, `JWT_PRIVATE_KEY`, `JWKS`, or `CALENDAR_TOKEN_SECRET` in any frontend code path
- **Never** prefix backend-only secrets with `VITE_` — anything with that prefix gets bundled into the JavaScript that users can download
- **Never** commit `.env`, `.env.local`, or `mastra/.env` — they are gitignored
- The only values safe to expose publicly are `VITE_CONVEX_URL` and `VITE_CONVEX_SITE_URL` (non-sensitive Convex endpoints)
